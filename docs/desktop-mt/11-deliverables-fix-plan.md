## 1. 问题与修法（共 9 项）

编号沿用审查清单。第 6、7、9、10、14、15 项已决定不修，见第 3 节。

### 插件：`plugins/desktop-deliverables/`

#### 第 1 项：同一文件在聊天里显示两次

**现象**：用户实测（小狗、关羽、小猫会话），同一张图片或视频出现两次。

**原因**：模型展示文件有三种写法，`transform()` 判断“已经展示过”时只认第一种。

| 写法 | 实例（来自真实会话） | 当前能否认出已展示 |
|---|---|---|
| 单独一行 `MEDIA:` | `MEDIA:C:\Users\stan\...\corgi_puppy.png` | 能 |
| Markdown 链接或图片，目标带 `MEDIA:` 前缀 | `![小狗](MEDIA:/C:/Users/stan/.../corgi_puppy.png)`，也见过 `![...](MEDIA:/C:\Users\...\puppy.png)` 这种斜杠混用 | 不能。`__init__.py:284` 的 `LINKS` 捕获到的是 `MEDIA:/C:/...`，`resolve_path` 解析不到同一路径 |
| 预览指令 | `::preview{file="C:/Users/stan/.../kitten.png"}`，属性值也可能用单引号 | 不能 |

**修法**：
- 在 `paths.py` 新增 `shown_paths(text, cwd)`，返回回复中已经以下列方式展示过的本机路径集合（每项都经 `resolve_path` 解析，丢弃 `None`）：
  - `LINKS` 捕获的普通链接目标；带 `MEDIA:` 的目标统一交给原版 `MEDIA_TAG_CLEANUP_RE`；
  - 不在独立行上的行内 `MEDIA:` 标记，复用 Hermes 原版识别规则，不再单独维护插件正则；
  - `::preview{...}` 指令里的 `file="..."` 或 `file='...'`。
- 先复用原版 `_mask_media_scan_text` 屏蔽代码、引用和存储示例，再排除独立 `MEDIA:` 行。示例既不算已经展示，也不能被移走。独立行由第 5 项的规则单独处理。
- `transform()` 用 `shown_paths` 替换现有的 `linked` 判断（`__init__.py:284-287`）。

#### 第 3 项：删掉 `MEDIA:` 行后原位置留下空行

**现象**：小狗 Word 会话中，模型写在正文中间的 `MEDIA:...docx` 被移到末尾，原位置留下 3～4 个连续换行。

**修法**：删除该行并收拢其两侧相邻空白，正文连接处最多保留两个换行（一个空行），兼容 LF／CRLF。只处理被删行所在的位置，不对整段回复做全局空行压缩；代码块中的 MEDIA 示例保持原样。

#### 第 5 项：模型写了的文件被删掉却没补回

**原因**：`__init__.py:270-287` 先按 `managed`（本轮全部候选文件）删除所有独立 `MEDIA:` 行，之后才：
- 在有文档时过滤掉图片；
- 截取前 8 个补回。

被过滤掉或排在第 9 个以后的文件，它们的行已经被删，就从回复里消失了。

**修法**：按下面的顺序重写这一段：
1. `shown = shown_paths(...)`（见第 1 项）。
2. 候选文件：保留现有规则（有文档时去掉图片，按 `priority` 排序），再去掉 `shown` 中已有的，取前 8 个，记为 `appended`。
3. 删除独立 `MEDIA:` 行，只删下面两种：
   - 路径属于 `appended`（稍后统一追加到末尾）；
   - 路径属于 `managed`，且同时已在 `shown` 里（模型对同一文件写了两种形式，保留非独立行那一处）。

   其余独立行一律保留在原位，包括被“有文档时去掉图片”过滤掉的图片行，以及第 9 个以后的文件行。
4. 末尾追加 `appended` 的 `MEDIA:` 行。

#### 第 4 项：Python 3.11 下整个插件失效

**原因**：`Path.is_junction()` 只在 Python 3.12 及以上提供，而仓库声明支持 `>=3.11`。当前有两处调用：
- `paths.py:154`
- `downloads.py:57`

**修法**：在 `paths.py` 新增一个 3.11 也能用的判断函数，两处都改为调用它。判断方法：
- 用 `os.lstat` 取文件信息；
- 符号链接（`stat.S_ISLNK`）算作链接；
- Windows 目录联接（`st_reparse_tag == stat.IO_REPARSE_TAG_MOUNT_POINT`，用 `getattr` 兼容非 Windows 平台）也算作链接；
- 路径不存在时返回 `False`，因为 `downloads.py` 的 `outputs` 目录可能尚未创建。
- 权限等其它 I/O 错误不能伪装成“不是链接”。扫描入口统一返回无效快照 `None`；遍历和元数据读取失败都不能保留部分基线，错误不向外中断钩子。下载沿用既有失败处理。

#### 第 8 项：任意工具失败就关闭本轮兜底扫描

**原因**：`__init__.py:217-219` 只要有任何工具结果不成功，就设置 `turn.guess = False`，于是本轮结束时不再对比目录。Hermes 里读文件、搜索失败很常见，这道兜底因此经常被关掉。

**修法**：只有可能写文件的工具失败时才设置 `guess = False`，即 `terminal`、`execute_code`、`write_file`、`patch` 这四个（可与 `before_tool` 的名单共用一个常量）。其他工具失败时只跳过对该结果的处理，不影响本轮结束时的扫描。

#### 第 11 项：重复扫描目录，扫描时持有全局锁

**原因**：
- `before_tool`（`__init__.py:165-193`）里，`watch_root` 首次观察某个目录时已经扫过一遍，紧接着 `snapshot(root)` 又扫同一目录；
- `after_tool` 再扫一遍；
- 三次扫描都在全局 `_lock` 内，同一后端中其他会话和账户的钩子都要等。

**修法**：
1. 首次观察目录只取得一份快照，复用为根基线与命令前快照。
2. 状态锁只保护内存记录。账号路径解析、目录读取、候选文件解析及元数据核查都在锁外；回锁后核对仍为同一轮。
3. 扫描完成前用 `None` 表示未取得基线，不能用 `{}` 占位。读取失败或超出预算时放弃对应目录的推断；`finally` 清理命令窗口及结束轮次，取消后的迟到结果不写回。
4. 执行窗口保持到文件核查结束。重叠目录的基线一旦作废，本轮不恢复；直接复用歧义标记，不增加序号或事件缓存。
5. 所有执行目录都参与冲突登记，“最多四个”只限制结束扫描。第五个目录也必须让其它会话察觉重叠；结束回复不再新增没有起始基线的目录。

### 界面：`apps/desktop/`

#### 第 2 项：`![说明](MEDIA:路径)` 显示后残留 `)`

**原因**：`src/lib/chat-messages/parts.ts` 的 `renderMediaTags()` 只把其中的 `MEDIA:路径` 替换成 `[文件名](#media:...)`，结果变成 `![小狗]([corgi_puppy.png](#media:...))`。Markdown 解析后多出一个 `)`。

**修法**：聊天渲染和产物提取共用按原文顺序消费的 MEDIA 解析器，将整个 `![任意说明](MEDIA:路径)` 或 `[任意说明](MEDIA:路径)` 替换为正式卡片：
- 支持尖括号目标 `(<MEDIA:...>)`；
- 支持路径中有空格及成对、嵌套括号；引号和尖括号内的括号属于文件名；
- 支持 `/C:/...` 和 `/C:\...` 两种斜杠写法；
- 说明文字丢弃。
- 生成的 `#media:` 链接对括号编码，避免下游再次误截断；产物列表对原文和渲染结果取得相同完整路径。

替换后的显示效果必须与单独一行 `MEDIA:路径` 完全一致。图片、视频、音频都要覆盖。

#### 第 12 项：打开旧会话时，Word 和 PPT 卡片全部在后台排队转换

**原因**：`src/app/chat/right-rail/formats/prepare.ts` 对每张挂载的卡片都调用 `prepareOfficePreview`（主进程走 `electron/office-preview/ipc.ts` 中 `background` 分支的 `hermes:office-preview:convert`），历史会话里的卡片也不例外。

**参考**：UniWork（`source.new-uniclaw/libs/hexagent_demo/frontend/src/components/FilePreview.tsx` 的 `PptxPreview`）只在用户打开预览时才转换，转换结果存入磁盘缓存，没有提前转换。

**修法**：只对新文件提前转换。在主进程处理后台请求时判断：
- 磁盘缓存已命中：照旧直接返回；
- 缓存未命中，且源文件修改时间和创建时间中较新的值早于当前 10 分钟以上：直接跳过，不入队。新复制或解压的文件即使保留旧修改时间，仍可预转换。

判断放在 `office-preview/service.ts` 的后台分支（该处已有 `source.stat`）或 `ipc.ts` 中，选改动更小的一处。用户点开预览走的是非后台请求，行为不变。

#### 第 13 项：去掉 PDF 卡片缩略图

**说明**：这是决定，不是缺陷修复。用户要求 PDF 卡片与 Word、PPT 等保持一致，只显示图标和文件名。

**修法**：
- 删除 `src/components/chat/pdf-thumbnail.tsx` 及 `pdf-thumbnail.test.tsx`；
- `src/components/chat/preview-attachment.tsx` 去掉导入（第 14 行）和 PDF 分支（第 134-135 行），所有类型统一使用现有图标；
- 同步修改 `preview-attachment.test.tsx` 中对 `./pdf-thumbnail` 的 mock 和相关断言；
- 只被缩略图使用的导出、样式或翻译键一并删除。删除前先全局搜索确认没有其他使用方；
- 修改 `docs/desktop-mt/10-deliverables-and-preview-plan.md`：B7 一行删去“PDF 附件首页缩略图”，第 195 行和第 198 行中关于缩略图的描述删除或注明已撤销。

## 8. 第二次复审修复（2026-10-19）

复审 `aa6b435556` 发现：锁外扫描为保证归属安全，加了“读失败就作废、有重叠就作废”的规则，结果正常情况下也会关掉兜底、漏补卡片。本次的处理：

- **扫描回到状态锁内**，只保留“目录刚登记时的基线直接作为命令前快照”的复用。锁外扫描带来的空字典占位、窗口收尾、迟到结果回写等问题随之消失。代价是扫描期间（最多约 0.5 秒）同一后端的其他会话钩子需要等待。
- **只有跨会话的目录重叠才标记“归属不明”**。同一轮里并行的两条命令只放弃各自的前后差异，本轮结束时的目录扫描照常；扫描超时或超量只让该目录没有基线，不再连带作废其他目录。
- **读不到的条目只跳过它自己**：扫描时把读不到或中途消失的目录、文件记为 `None`，前后对比时这些位置下的文件不参与比较。既不会因为一个没权限的子目录整次作废，也不会在权限恢复后把读漏的文件当成新增。`is_dir` 在 Python 3.11 遇到无权限会抛错，统一改为安全判断；工具输出里有读不到的路径时，明确写出的文件照常补卡。
- **`[说明](MEDIA:相对路径)` 也算已展示**，不再重复补卡。回复的示例屏蔽只做一次，两处识别共用。
- **会话结束事件核对轮次**，上一轮迟到的结束事件不再清掉新一轮。
- **界面解析器**：Markdown 包装先换成占位符，再对整段文本识别，链接后面同一行的裸 `MEDIA:` 不再被当成独立行（不吞后文、不吃空格）。
- Office 测试在不记录创建时间的文件系统上跳过“复制模板”一项。

## 2026-10-19 补充：元景成品下载到本机

实测发现：生成的图片一直没有自动下载（图片链接是 `http://`，上次放行只认 `https://`），模型只好把 OSS 链接写进回复，卡片点开是 OSS 地址；视频虽能下载，文件名却是随机码。本次在 `plugins/desktop-deliverables/downloads.py` 和 `__init__.py` 中调整：

| 项 | 现在的做法 |
|---|---|
| 放行协议 | 生图成品目录同时放行 `http`、`https`（限默认端口）；其它工具仍只放行 `https` |
| 文件名 | 取生成时的描述（`prompt`／`text` 等）前 24 字，去掉 Windows 非法字符、避开设备保留名；翻译沿用原文件名加“_翻译版／_中英对照版”；取不到时用“生成图片／生成视频／语音／AI播客／翻译结果”。同名加 `-2`、`-3`，独占创建，不覆盖已有文件 |

## 2026-10-19 补充：素材目录只在工作目录里面判断

插件把 `templates`、`assets`、`scripts` 等目录和以点开头的目录当作素材，不出卡片。原来检查的是文件的完整路径，用户选的工作目录本身或它的上级叫这些名字（例如 `D:\assets\季度汇报`）时，整轮生成的文件都不出卡片。

现在 `paths.py` 的 `eligible` 只检查文件在所属工作目录（本轮终端目录及用户本次指名的目录，取最深的一个）里面的那段路径；工作目录里面的素材子目录照旧排除。不在任何工作目录里的文件仍按完整路径判断。命令前后的快照对比按同样规则处理。

## 2026-10-20 补充：调用元景工具时自动上传本机文件

元景工具在远程，读不到本机路径。以前模型要先试 `vision_analyze`、再查上传工具、自己做"取上传地址 → curl 上传 → 确认"三步，一次图生视频要调十来次工具。新增 `plugins/desktop-deliverables/uploads.py`，参考 UniWork 的 `SandboxUploadMiddleware` 和 postgresql-multitenant 的 `pre_upload.py`：

| 项 | 做法 |
|---|---|
| 什么时候传 | 只在模型调用元景工具、参数里填了本机文件时（`pre_tool_call` 的 `modify`）；不用元景就什么都不传，不做预传 |
| 管哪些工具 | 带 `get_oss_upload_url` 的远程 MCP 服务器的全部工具，上传工具本身除外；文字参数和列表里的每一项都看 |
| 允许的文件 | 账号 Home 的 `attachments`、当前工作目录、本会话里用户 `@file:`／`@image:` 引用过的文件（从会话历史读，重启不丢）；其它位置拦下并说明，不上传 |
| 换成什么 | ossPath（如 `app-agent-prod/temp/xxx.png`），不调 `confirm_oss_upload`，不带签名、不会过期；上传地址只认固定对象存储的 `/app-agent-prod/temp/` |
| 重复使用 | 按"路径 + 修改时间 + 大小"缓存一天 |
| 失败 | 拦下这次调用，说明卡在"取上传地址"还是"上传文件"；日志不记签名链接 |
| 提醒模型 | 元景已连接时每轮在本轮上下文里加一句：直接填本机路径，不要自己上传，看图用 `analyze_image` |
