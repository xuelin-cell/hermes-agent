# 阶段二：entry_local 与账号环境

状态：计划，尚未实施。对应原步骤 9～12，前置边界见 [总计划](README.md)。

本阶段在独立验收目录中启动原版 Hermes。P17 完成前只做固定账号或完整退出进程后的测试，不提供尚无完整隔离的日常换账号入口。

## P11 · 稳定账号目录与默认工作目录

- 提交主题：`feat(entry-local): 按可信账号选择独立本地目录`。
- 预计位置：`electron/entry_local/account-paths.ts` 和账号环境准备入口。
- 行为：平台命名空间＋UID 映射到固定安全目录标识；拒绝路径穿越、系统保留名或脱离受管根目录的目标。映射细节在本提交固定并测试。
- 新账号创建 `hermes-home` 与 `workspace`；已存在的环境复用。Key/token 更新不能生成新目录；不自动导入旧无账号数据。
- 自动检查：临时根目录下 A→B→A、特殊 UID、路径归属和重复初始化；使用真实文件系统验证 A 的标记文件在 B 中不可见。
- 真实验收：两个测试账号准备后人工查看目录和默认工作目录；夹具账号须标明为模拟身份，不视为真实 MaaS 登录证明。
- 边界：只接受主进程可信登录结果。Renderer 传 UID 或路径不能改变账号位置；创建目录不等于完整账号隔离已完成。

## P12 · 只合并 MaaS 的模型配置

- 提交主题：`feat(entry-local): 合并 MaaS 模型配置并保留用户设置`。
- 预计位置：`electron/entry_local/model-config.ts`；使用现有 `yaml` 解析能力，先核对类型和保留用户字段的行为。
- 行为：首次初始化可以设置 MaaS 默认模型；已有配置只维护 MaaS provider 的字段，保留自定义 provider、用户选择、MCP、Skills 及其他设置。
- 平台 provider 标识由产品固定管理；碰到无法确认归属的已有同名配置时不能直接覆盖，提供明确冲突信息。
- 自动检查：用真实 YAML 文件验证首次创建、重复登录、用户改默认模型、未知字段、损坏文件和多端点模型。不同端点不能全部错误地指向主模型地址。
- 本提交验收：准备含个人 provider 的样例账号 Home，调用真实配置写入函数并重新读取，核对个人模型与默认选择；这是实际文件验证，不是完整界面验收。
- P15 接入后补验：刷新 MaaS 配置并重新打开原版设置页面，确认个人模型与默认选择显示正确。
- 边界：损坏配置停止本次准备并提示修复，不重置文件；查询失败不作为删除全部 MaaS 模型的指令。

## P13 · 写入账号内模型 Key

- 提交主题：`feat(entry-local): 更新账号 MaaS 模型凭据`。
- 行为：复用原版支持的 Key 引用方式，在账号自己的配置／`.env` 中只更新 MaaS 专用变量；避免账号之间或与个人 Key 共用一个变量。
- 说明：MaaS 登录 token 保持系统加密；原版 Hermes 从 `.env` 读取模型 Key 时，该文件不因此自动加密。按账号限制文件访问，不宣称所有模型凭据都以密文落盘。
- 自动检查：重复更新、Key 更换、写入中断、无套餐与查询失败；临时文件使用同样保护，日志只记状态，不打印内容。
- 真实验收：用替身 Key 检查只改变指定变量，其他变量及个人 Key 保持；在临时进程环境中确认读取的是该账号 Key，不输出原值。
- 边界：可信确认套餐取消后，清除平台托管凭据或按核实的配置机制使其不可用；未知／网络失败不删除旧值，也不把旧值当成刷新成功。首次写配置未完成不得启动后端。

## P14 · 固定一次运行的账号上下文

- 提交主题：`refactor(entry-local): 分离运行时安装位置与账号数据路径`。
- 预计位置：`electron/entry.ts`、`data-paths`、小型账号启动上下文与 `main.ts` 接线。
- 行为：账号获准进入后，固定本次进程的账号 Home、工作目录和状态目录，再初始化依赖这些路径的运行时；安装目录继续指向同一开发仓库。
- 核查所有启动时读取路径的入口。预先保存的账号选择标识只是定位提示，不能绕过 Login 验证直接成为授权。
- 自动检查：运行时解析仍选开发仓库和现有 Python；A/B 账号只改变数据位置。未登录、无效记录和手工改定位提示不能启动旧环境。
- 真实验收：检查启动状态显示的目录与实际生成文件；X 盘官方安装和现有无账号 Home 均未被认领。
- 边界：不动态修改旧进程的 Home 进行换账号；本提交不顺便安装或升级 Python 依赖。

## P15 · 启动并连接当前账号的原版 Hermes

- 提交主题：`feat(entry-local): 启动并连接账号本地 Hermes`。
- 预计位置：`entry_local`、`main.ts`、`local-backend-lifecycle.ts`、`source-backend.ts` 的现有调用接线。
- 行为：准备好账号配置后启动后端，只监听回环地址，使用原版独立本地连接凭据；页面按原版方式使用 REST／WebSocket。
- 重复启动请求共享一个进行中的启动。端口、Profile 和后端归属必须一致；不得误连机器上已有的官方 Hermes。
- 自动检查：真实临时 Home 启动后端，验证健康检查、本地鉴权和同账号重复连接；不需要付费模型即可验证启动链。
- 真实验收：用户明确发起一次最小模型对话、一次临时工作区文件操作；确认历史和文件属于当前账号，退出重开可恢复。
- 边界：此时尚未完成全部退出规则；只在受控验收环境使用，不启动尚未覆盖停止机制的网关或后台服务。

## P16 · 隔离主进程持久状态

- 提交主题：`feat(entry-local): 按账号保存桌面连接与工作区状态`。
- 预计位置：账号状态路径模块，`main.ts` 中连接、active-profile、默认项目、附件缓存等现有读写点。
- 行为：明确应用级与账号级文件；连接注册、默认项目、活动 Profile、账号凭据缓存及临时附件归属账号。窗口尺寸等设备偏好可保持应用级。
- 自动检查：在两个临时账号中通过真实存储函数分别写读，确认相同 Profile 名、相同会话标识不会互相覆盖。
- 真实验收：A 设置项目和 Profile 后完整关闭，再以 B 打开，确认不出现 A 的项目选择；回 A 后仍保留原选择。
- 边界：不以改动 Electron 全局 `userData` 根目录代替分类；不覆盖应用锁、安装位置和公共登录记录。

## P17 · 隔离 Chromium 存储和 Renderer 状态

- 提交主题：`feat(entry-local): 隔离账号窗口存储与聊天草稿`。
- 预计位置：Electron 会话／窗口创建、`session-windows.ts`、必要的 Renderer 启动接线。
- 行为：用 Electron 现有 session／partition 机制隔离 Cookie、localStorage、IndexedDB、预览网页存储。主窗、会话副窗、HUD、Quick Entry 等账号窗口必须采用一致归属。
- 必须在对应 Session 首次使用前确定路径／分区；不能账号 A 已创建默认 Session 后，仅改环境变量声称变成 B。
- 自动检查：真实 Electron 两个账号分区读写相同存储键；销毁旧窗口后，延迟请求不能更新新账号状态。纯 Node 单测不替代 Chromium 验证。
- 真实验收：A 输入未发送草稿、选择会话和项目，退出进程后打开 B，再回 A；B 无 A 草稿，A 草稿可恢复。检查预览页登录状态也不会跨账号继承。
- 边界：不删除用户草稿来伪装隔离成功；不引入每次退出清空整个应用缓存的做法。

## 阶段出口

- 当前账号能够使用原版 Hermes，文件、会话与界面持久状态均有 A/B 隔离证据。
- 相同账号重新打开能复用数据，个人模型与工具设置保留。
- 完整账号退出、过期和后台工作停止仍由阶段三验收；不能在这里宣布产品已经可安全换账号。
