边界：没有修复核心插件加载器的 `dictionary changed size during iteration` 异常，也没有强制重载插件。修复的是桌面状态对该进程注册结果的错误依赖；如果网关进程本身未加载／连接钉钉，仍只能显示未就绪或原版提供的错误。更新后需用户完整退出开发版（含托盘）再启动，以加载新的桌面后端和网关插件。

## 目标和边界

用户配置微信、钉钉、飞书、企业微信智能机器人后，由桌面自动完成连接；再次打开应用时恢复当前账号已启用的平台。补齐钉钉原生图片、文件发送，其它平台复用已有能力。

- 保持 `hermes serve` 与 `hermes gateway` 分进程。Electron 管理账号和生命周期，Renderer 展示结果，原版 Hermes 继续执行消息、会话和工具。
- 不修改 Hermes Python 后端核心，包括 Agent 执行、会话存储、网关通用调度和鉴权判断。允许在已有官方钉钉平台插件中补齐发送能力，允许新增 `plugins/desktop-messaging/` 插件路由，也允许修改定制桌面代码与已有微信扫码插件。
- **配置生效统一采用整个网关自动重启（2026-10-18 用户已定）。** 本轮不做单平台重连，也不再评估；改一个平台时其它平台会短暂断开，界面如实提示。原因见下方“单平台重连为何本轮不做”。
- 不为本轮新建渠道子进程调度系统，不强行拆成每平台一个完整 Hermes；不开展网关重启性能优化。
- 范围限桌面本地多账号。保持现有 Profile 作用域，不改变手机与桌面的会话组织、历史、记忆和工具行为。
- 企业微信只填写 ID、Secret；个人微信继续扫码。不新增企业微信扫码创建、AI 卡片、5G、UniBot 或 Windows 开机自启动。
- 飞书回复样式、各平台已有等待反馈、微信音频附件回复保持现状。企业微信语音直接可用则保留；确实不可用则按约定忽略，不新增语音识别，也不将这项规则扩大到其它平台。

| UniWork 客户端参考 | 本地 `source.new-uniclaw @ 8ae3548e03`。后端启动渠道，配置变化后按平台重建连接；三种 ID／Secret 配置有在线校验 |

Hermes 的 `hot_served` 只在“多路网关服务的命名 Profile”时为真（`messaging.py` 的 `_notify_multiplexer_hot_serve`），桌面账号使用默认 Profile，因此保存后永远需要重启，不能把它当作已生效。

### 单平台重连为何本轮不做

- 原版网关内部已有逐个平台重建连接的代码（`gateway/run_adapters.py` 的 `_reconnect_failed_platform`，用于断线重连），但没有从外部让“在线平台”重连的入口；`/platform pause|resume` 只作用于重试队列里的失败平台，`reload-plugins` 控制命令只重挂消息处理程序、不换凭据。补这个入口需要修改网关核心。
- 参考分支能单独重连，是因为它不经过 Hermes 网关：每个用户×平台一个 worker 进程，只借用 Hermes 适配器收发，收到消息后由它自己的 Web 后端（`webapp/uniclaw_api.py` 的 `_handle_channel_inbound`）做授权、会话归属、去重和执行。照搬等于重写原版消息处理，违背本计划边界。
- 结论：本轮整个网关重启。以后若要做，路线是“给网关加重连指定平台的控制命令，复用上述重建代码”，需另行评估并经用户同意修改核心。

三个阶段均交付功能，验证随对应步骤完成。没有单独的“整体验收阶段”。

## 阶段一：保存配置后即可连接

交付结果：用户在当前消息平台卡片中保存有效配置，应用自动连接；错误凭据不覆盖旧配置，无需终端配对命令或手动切换页面。

### G01：保存和解绑后自动重启网关

- 采用既有网关启动／重启机制（`runGatewayRestart` 等），不评估单平台更新，不通过内部对象替换、猴子补丁或虚构 Profile 绕过限制。
- 先核实网关未运行时既有“重启”动作是否会直接启动；不会则补上“未运行就启动”的分支，仍只调用原版接口。
- 让普通保存和解绑进入同一套配置生效流程。微信插件已发起的重启只跟踪结果，避免重复重启。
- 未改变的配置不重复重启。保存成功而启动失败时保留已保存配置，允许用户明确重试连接，不伪装为保存失败。
- 解绑后若已没有任何启用且配置完整的平台，直接停止本账号网关，不再重启一个空网关；与 G04“无配置不启动”一致。
- 提示连接正在恢复，并说明其它已连接平台会短暂断开；保留原版停止和收尾语义。

主要模块：`apps/desktop/src/app/messaging/`、消息 API 与系统操作模块、Electron 主进程中的账号操作模块；原版重启接口仅调用。

完成检查：使用隔离账号目录验证保存后自动启动／重启、重复点击不会并发操作、微信只触发一次重启、失败可重试、解绑最后一个平台后网关停止。

### G02：凭据变更先校验，成功后再保存

- 校验放在新增的官方插件路由 `plugins/desktop-messaging/dashboard/`（`manifest.json` + `plugin_api.py`，挂载到 `/api/plugins/desktop-messaging/`），写法参照 `plugins/weixin_qr/dashboard/`。不在 Electron 主进程用 TypeScript 重写各平台协议。
- 各平台校验方式，尽量复用 Hermes 现有代码：
  - 钉钉：用 AppKey／AppSecret 换取 access token（参考 `plugins/platforms/dingtalk/adapter.py` 的 `_get_access_token`）。
  - 飞书：换取 `tenant_access_token`（参考 `plugins/platforms/feishu/adapter.py` 的 `probe_bot`／`_probe_bot_http`）。`probe_bot` 失败只返回 `None`，无法区分凭据错误与网络错误时需自行判断响应。
  - 企业微信：与 UniWork 相同，短暂试连一次（用户已定）。复用企业微信插件的连接与 `aibot_subscribe` 握手（`_open_connection`／`_wait_for_handshake`），收到成功或错误应答后立即断开；超时约 12 秒。
- 只在 ID 或 Secret 有变化时校验；未修改的已保存凭据不重复验证。脱敏占位不能当作真实 Secret；修改 ID 时必须取得与之对应的真实 Secret，不能拿旧占位值组合请求。
- 企业微信试连可能顶掉同一机器人正在运行的连接。由于只在凭据变化时发生，且保存成功后网关随即重启，可以接受；校验失败时如旧连接被顶掉，依靠原版断线重连恢复，记录实测现象。
- 验证失败不写入新凭据、不重启网关；区分认证拒绝、超时、网络失败和异常响应，不在日志、提示中输出 Secret。
- 同机另一账号已在使用同一机器人（同平台同 ID）时，保存前提示并要求确认，避免两个网关抢同一连接。跨账号比对只在 Electron 主进程保存 ID 的摘要，不读取其它账号目录、不暴露其它账号信息。
- 仅允许当前可信账号和固定平台操作；页面不指定账号目录、任意请求地址或 shell 命令。

主要模块：配置弹窗、新增 `plugins/desktop-messaging/` 插件路由、桌面 API 封装与类型定义；跨账号提示放在 Electron 主进程账号模块。继续复用原有配置写入能力。

完成检查：错误凭据、网络超时和异常响应均保留旧配置；未变更 Secret 不被覆盖；同机重复使用同一机器人有提示；真实请求链路可由受控上游验证。真实平台认证另记证据，不把受控响应写成真实平台通过。

### G03：简化首次授权，连接状态跟随实际结果

- 准入规则与 UniWork 一致（用户已定）：UniWork 不设白名单和配对，平台推送过来的私聊、群聊消息都处理，谁能使用机器人由企业后台可见范围决定。不能把 MaaS 登录账号推断为 IM 发信人。
- 只用原版支持的配置项表达，不修改 `gateway/authz_mixin.py` 等通用鉴权实现。保存凭据成功时写入：

  | 平台 | 写入的设置 |
  | --- | --- |
  | 钉钉 | `DINGTALK_ALLOW_ALL_USERS=true` |
  | 飞书 | `FEISHU_ALLOW_ALL_USERS=true`、`FEISHU_GROUP_POLICY=open` |
  | 企业微信 | `WECOM_ALLOW_ALL_USERS=true`、`WECOM_DM_POLICY=open`、`WECOM_GROUP_POLICY=open` |

- 这些字段原版保存接口不接受，由 G02 新增的 `desktop-messaging` 插件路由写入，参照 `weixin_qr` 插件 `_apply` 的写法（`_profile_scope` + `save_env_value`）。路由只写上表固定键值，不接受页面传入任意键。
- **禁止写 `GATEWAY_ALLOW_ALL_USERS`**：它对所有平台生效，会让微信也对任何人开放。
- 群聊是否要求 @ 机器人沿用 Hermes 各平台原有设置，不新增规则。实施时沿真实入站路径逐个平台验证私聊和群聊都能进入执行；若仍有原版设置拦截，改为放行并在本文记录。
- 已经配置过的平台（升级前保存的）没有上述设置，在 G04 自动恢复启动网关前补写一次，不要求用户重新保存。
- 保持微信扫码人绑定和群聊规则。缺少可信扫码人标识时明确显示绑定未完成，不静默放开所有用户，也不将终端配对命令作为正常完成流程。
- 配置保存、网关动作完成、渠道连接成功分别处理；连接中、失败与重试结果在当前页面自动更新，迟到结果不能覆盖新账号或新 Profile。
- 解绑只关闭对应平台配置并按 G01 重启或停止网关，保留历史、文件与其它配置。

主要模块：`desktop-messaging` 插件路由、消息卡片和状态刷新、已有微信扫码插件的边界处理。

完成检查：钉钉、飞书、企业微信的私聊和群聊首条消息不要求配对命令；未写入 `GATEWAY_ALLOW_ALL_USERS`，微信不能被其它身份借此访问；配置完成但连接失败时不能显示已连接；变更不污染其它账号／Profile。

## 阶段二：打开应用自动恢复消息平台

交付结果：登录或恢复登录后自动准备该账号消息连接，用户无需进入消息设置页；连接失败不阻塞桌面聊天。

### G04：账号准备完成后后台恢复网关

- 在主进程建立可信账号上下文后，检查当前账号默认环境及现有受管 Profiles 中的启用配置，沿用原版运行范围，不凭目录存在就认定需要启动。
- 没有已启用且配置完整的平台时不启动 IM 网关；有配置时复用身份、Home 和归属均符合的现有进程，未运行才启动。
- 使用当前账号已准备的 Python、Home 与环境；不寻找或复用官方安装版，不另行安装系统自动启动项。
- 桌面后端按原流程启动；IM 恢复在后台进行，失败只影响消息平台功能。
- 启动网关前，对已启用的钉钉、飞书、企业微信调用 `desktop-messaging` 路由补写 G03 的准入设置（已存在且一致则不写）。

主要模块：`electron/entry_local/messaging.ts`、`desktop-messaging` 插件和主入口少量接线；复用已固定的账号上下文与原版后端连接池，不另建运行服务。

完成检查：无配置不启动、有配置自动启动、已运行不重复启动；旧配置补写准入设置后首条消息无需配对；身份 A→B→A 的进程和配置归属正确；自动恢复不依赖打开消息页面。

### G05：统一处理启动、保存和退出之间的竞争

- 自动恢复与阶段一的保存／解绑操作共用最小必要的协调逻辑，避免同一账号同时启动和重启多个网关。
- 串行处理确有变化的配置；操作期间出现新变更，最终以最新成功保存的配置为准，不丢弃用户意图。
- 退出开始后不接受新的启动操作，已在进行的恢复不能在退出检查之后重新拉起旧账号网关。
- 接入现有归属记录和停止流程；停止失败继续保留记录，禁止未经确认归属就结束进程。

主要模块：账号网关操作、已有 `gateway-logout`、`logout` 和 `recover-account` 接线。

完成检查：启动中退出、保存中退出、连续保存、解绑与自动恢复交错；完成退出后没有新拉起的旧账号网关，原有停止失败处理有效。

### G06：后台连接异常可见且可恢复

- 复用原版平台重连，不新增与 SDK 或网关竞争的重连循环。
- 对自动启动失败和连接异常提供简短提示、明确重试入口及现有日志入口；不显示无期限加载状态。
