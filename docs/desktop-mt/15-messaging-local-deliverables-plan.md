# 消息会话复用桌面本机成品交付：单次提交方案

日期：2026-10-23 定稿，2026-10-25 实施。分支：`release`。实施基线：`02025cc061`（含协作者 `30c556dcac` 新增的 `workspace()`，消息下载目录沿用它）。

状态：已实施并通过定向自动化测试，见文末“实施记录”。真实平台收发未验收，本文件不是验收通过记录。

## 目标

把桌面已经使用的“识别生成成品 → 自动下载 → 补充 MEDIA 本机文件引用”扩展到消息会话。微信、飞书、企业微信复用各自已有的本地附件发送；钉钉复用已有图片和普通文件能力，不新增视频发送或视频转文件附件方案。

普通会话与后台任务都需要接通。下载成功时使用本机成品，不把远程链接作为正常交付；下载失败沿用桌面现有行为：保留失败成品的原链接并说明，不能补不存在的 MEDIA 路径。

## 不做什么

- 不修“结果不可用”及桌面工具运行状态。
- 不修改 Hermes 核心、网关公共调度、平台发送器或桌面预览组件。
- 不做钉钉视频发送。该场景保持原有行为，不套用本次本地视频交付规则，不移除其原链接，不新增视频 MEDIA 自动补齐。
- 不改 MCP 连接锁、排队、超时或生成调用策略。
- 不新建下载器、任务队列、重试系统、数据库表、配置项或依赖。
- 不做压缩、转码、媒体内容校验扩展、缓存清理或大文件专项。
- 不把桌面扫描普通工作文件、猜测新增产物的能力推广到消息渠道。本次只交付现有生成工具返回、由插件实际下载成功的文件。

## 采用方式与复用范围

采用“扩展既有插件接线”，不采用提示模型自己下载，也不在每个平台各写一份下载逻辑。

- 下载工具白名单、URL 解析、可信成品来源检查、命名、`outputs` 位置、大小与时间限制、半成品写入、下载去重继续复用。
- 桌面同步与后台路径不改变功能语义；消息路径使用相同下载结果和文件引用处理。
- 后台任务使用已有的 Hermes 原生委派与完成回传，不新建任务系统。与桌面对齐视频业务的后台指导，但不把图片等其他工具强制改成后台运行。
- `MEDIA` 在桌面解释为卡片，在消息渠道解释为原有附件发送。插件不直接调用平台接口，不广播、不另用 send_message 发送一份结果。
- 现有账号／Profile／会话作用域继续沿用，不另建账号或目录映射。

## 预计修改的六个业务模块

| 模块 | 修改内容 |
| --- | --- |
| `plugins/desktop-deliverables/__init__.py` | 为目标消息会话登记下载上下文；跳过桌面目录扫描和普通工具产物猜测。回复结束时复用已有文件引用、存在性判断和去重，只补本轮下载的成品。保留桌面原路径。 |
| `plugins/desktop-deliverables/background.py` | 后台子任务继承父会话目录及原消息来源，避免扩展消息主会话后被误判成桌面。把支持渠道的视频后台缓存接到现有路径，保留翻译、播客能力；钉钉视频不纳入新交付规则。尽量合并重复登记，不增加第二套状态表。 |
| `plugins/desktop-deliverables/downloads.py` | 复用现有去链接函数：消息成品下载成功后也去掉对应链接，返回本机路径；消息说明不承诺桌面卡片。失败仍按桌面保留链接。实际 HTTP 下载函数原则上不改。 |
| `plugins/uniwork-kits/background_rules.py` | 消息视频任务复用桌面已有委派及完成回传指导，按来源保留钉钉视频例外。统一“成功返回本机成品、失败沿用原规则”的说明，不改旧会话被冻结的系统提示。 |
| `plugins/desktop-deliverables/uploads.py` | 自动上传的允许范围加上本账号收到的消息附件目录（Hermes 媒体缓存里的图片、文档、音频、视频），见“核对后需补上的问题”第 8 条。 |
| `plugins/desktop-deliverables/image_hints.py` | 看图提示改写从只限桌面放开到四个消息平台，并认出网关预先看图时的三种写法，见“核对后需补上的问题”第 9 条。 |

钉钉视频例外需要来源在后台任务内保持可辨认，不能只使用一个“是否消息渠道”的布尔值。只记录现有来源，不新增用户配置或第二套路由。

成功成品的文件引用应由程序补齐，不能只依赖模型遵循新提示。已有消息会话同样应能在下一次生成时使用下载钩子；新版冻结的后台委派指导仅在新会话生效，测试需区分这两件事。

回复移除链接只针对本轮已成功下载的成品原链接，不删除用户正文中的其他网址。失败、未支持及钉钉视频的原链接不冒充已下载。

## 核对后需补上的问题

对照代码核对后补充，各项均已与 Stan 确认，按此实施。

1. **后台完成那一轮也由程序补 MEDIA。** 后台任务完成后，Hermes 把完成通知作为新消息交给父会话，父会话模型再回复一轮。这一轮本身没有下载，只补“本轮下载”就补不上，只能靠模型照抄。做法：子任务下载成功时，按“账号＋父会话”记下成品；父会话收到完成通知那一轮，由程序补上对应 MEDIA，并与模型自己写的去重。桌面后台路径也一起受益。记录要等成品真正补进回复才清掉：完成那一轮被打断（消息平台用户发图片、文件、语音，或桌面点停止）时，下一轮回复照样补上，可能跟在不相关的回复后面，但不会丢。不能在被打断的那一轮补：网关会整段丢弃被打断那一轮的回复（`gateway/run_turn.py` 中“Interrupted: discard the response”），要改只能改网关。用户发消息打断时，网关紧接着就用这条消息开下一轮，视频会跟在这条回复后面出来；只有 `/stop`（桌面是点停止）之后没有新消息，要等用户下次说话。注意 Hermes 每轮结束都会发 `on_session_end`（不只是真正结束会话时），所以不能在这个钩子里清这份记录。记录按“账号＋会话”保存，补出后即清；未补出的最多保留最近 128 个会话，超出按最久未用淘汰。`/new` 后会话号改变，旧记录不会补进新会话；不跨会话、不跨账号。
2. **超过 20MB 的成品不删链接（已定）。** 附件发不出去时，如果链接已经删了，用户就什么都拿不到。四个平台统一按 20MB 判断：20MB 以内删链接、只发附件；超过 20MB 照常下载并尝试发附件，同时保留原链接。20MB 是企业微信文件和钉钉的硬上限；飞书（约 30MB）和微信（上限未知）按此偏保守，最多多出一条链接。企业微信视频超过 10MB 会被改成文件发送，用户仍能收到，不算失败。

   | 平台 | 图片 | 视频 | 其他文件 | 依据 |
   | --- | --- | --- | --- | --- |
   | 企业微信（机器人） | 10MB | 10MB，超过改成文件发 | 20MB，超过拒发 | `plugins/platforms/wecom/media.py` |
   | 钉钉 | 20MB | 本次不发视频 | 20MB | `plugins/platforms/dingtalk/media.py` |
   | 飞书 | 10MB | 30MB（按文件上传） | 30MB | 飞书官方接口文档，代码里没写，未查证 |
   | 微信 | 未知 | 未知 | 未知 | 代码和公开资料都没有，需实测 |

3. **已有消息聊天的后台视频：不处理（已定）。** 消息机器人的一个聊天长期只有一个会话，系统提示在会话开始时就固定了，新的委派规则只在新会话生效。已有聊天里的视频仍在主会话同步生成，但同样会下载成附件发送，只是用户要多等一会。不加每轮提示，也不写进使用说明。
4. **只开微信、飞书、企业微信（机器人模式）、钉钉（已定）。** 现有代码对“消息渠道”用的是排除法。Telegram、QQ、元宝等其他平台保持原有行为，不跟着删链接。
5. **企业微信只支持机器人模式。** “自建应用回调”模式只能发文字，保持原有行为，不删链接。
6. **消息会话不参与桌面目录核对。** 消息会话的本轮登记只服务于下载和补 MEDIA：工具调用前后都不扫描、不登记目录，不能因为与桌面会话目录重叠，导致桌面的卡片被作废。
7. **流式平台单独验证。** 飞书、钉钉可以编辑已发出的消息；插件改写回复后，网关会把已发的流式消息编辑成改写后的全文。需要验证用户看不到 `MEDIA:` 文字，附件只发一次。
8. **消息平台收到的文件也自动上传（已定）。** 用户在消息平台发来的图片、文档存在账号的 Hermes 媒体缓存目录（如 `cache\images`、`cache\documents`），不在上传插件的允许范围（桌面附件目录、当前工作目录、`@file:` 点名的文件）里，图生视频、图片编辑、文档翻译第一次调用会被拒，要模型先复制文件再调一次，有的模型会直接放弃。做法：允许范围加上本账号的这些缓存目录，它们都是用户自己发来的文件，与桌面附件同性质；其他账号的目录和凭据仍不可上传。
9. **消息平台的看图提示也改成元景看图（已定）。** 主模型看不了图时，桌面把 Hermes 的“用 vision_analyze 看图”提示换成元景 analyze_image，但这项只对桌面生效；账号配置里 vision 工具是关掉的，消息平台的模型会被引向用不了的工具，可能看不到图或编造内容。做法：平台判断放开到四个消息平台；网关预先看图时有三种写法（看图成功、看不清、出错），与桌面不同，其中成功那种路径后面多一个“ ~”，三种都要认出并保留正确路径，只换提示、不改路径。主模型能看图时不改写，与桌面一致。

使用说明需写明：消息成品都存在账号默认工作目录下的 `outputs`，各聊天共用，不自动清理；视频下载最多等 20 秒，超时就退回发链接。

## 验证安排

先复用现有 `desktop_deliverables_generated_fixture.py`、下载 HTTP 夹具及以下相关测试，新增最少的行为场景。不是每次小修改都运行全量测试。

1. **同步路径**：微信、飞书、企业微信生成图片／视频，钉钉生成图片。使用受控模型和本机 HTTP 返回真实临时文件，即使最终模型回复只有“完成了”，插件仍自动下载并补齐唯一 MEDIA 引用；成功结果不带成品原链接。
2. **后台路径**：文生、图生视频沿原生委派完成回传到原消息会话；父会话模型回复里不抄 MEDIA 时，程序仍能补上唯一引用。完成那一轮被打断时，下一轮补上且只补一次。翻译、播客不退化。钉钉视频仍不新增本地视频交付。桌面原有同步／后台路径回归。
3. **真实附件分派**：文件经过原版 MEDIA 解析及路径检查后，进入已有适配器的本地图片／视频／文件发送方法；使用受控传输，不调用真实平台或付费生成服务。测试不能只断言回复里有路径。包括飞书开启流式、回复被插件改写后编辑已发消息的场景。
4. **用户发来的文件**：消息平台发来的图片、文档能自动上传给元景（图生视频、文档翻译不被拒），其他账号目录仍拒；主模型看不了图时，网关三种看图提示都被换成元景看图且路径正确。
5. **基本边界**：同名不覆盖、并发会话只拿自己的文件、账号 A→B→A、取消后的迟到结果不入新轮、不重复下载／补文件引用。
6. **失败路径**：下载失败保留原链接、不补假路径；超过 20MB 的成品既有附件也保留原链接；附件投递失败沿用适配器现有失败提示，不自动重新生成。

## 实施记录（2026-10-25）

实际改动与上表六个插件文件一致，没有改 Hermes 核心、网关、平台适配器或桌面界面。几点实现细节：

- 四个平台的名单集中在 `desktop-deliverables/background.py` 的 `DELIVERY_PLATFORMS`，看图提示也引用它；`uniwork-kits` 是独立插件，`background_rules.py` 里另有一份同样的名单，注释写明两处要一致。
- 后台成品什么时候补：父会话收到的消息里出现了这个成品的本机路径（也就是后台完成通知）才补，免得在完成通知到达前的闲聊里先补一次、完成那轮模型再抄一次而重复发送。完成通知若不含路径，回到靠模型照抄。
- 每条回复最多补 8 个附件，与桌面卡片上限相同；没补出的后台成品留到下一轮。
