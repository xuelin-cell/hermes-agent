# 云端入口是否保存 MaaS 登录令牌：决策说明

- 更新日期：2026-10-26
- 核查基线：`release` 工作区，HEAD `cc6e7ccd82`
- 状态：方案讨论，尚未实施
- 目标：决定云端入口是否保存用户 MaaS 登录 token，以及保存的范围和生命周期，为分享及其他功能迁移提供依据。

## 本轮重点：两种实际可选的保存位置

两种方案都沿用用户 MaaS token 调用现有分享网关；区别是 token 放在浏览器还是入口。两种方案都需要入口识别当前用户、验证分享归属，并处理 token 过期。下面说的“持久化”指把**加密后的 MaaS token**存到入口的 PostgreSQL；不是让 PostgreSQL 用 MaaS token 鉴权。入口连接数据库继续使用独立的 `MT_DATABASE_URL` 凭据。

| 决策点 | 方案一：浏览器保存，参考 UniClaw `cloud-vm-dev` | 方案二：入口加密持久化 |
|---|---|---|
| 登录后保存 | 入口把 MaaS token 返回页面，页面存 `localStorage`；同时保留现有入口 session 用于云端实例路由 | 入口不把 MaaS token 返回页面，按入口登录 session 加密写入 PG；页面仍只拿入口 session cookie |
| 分享请求 | 页面在调用入口分享接口时附带 MaaS token；入口须通过可信上游校验或有效签名验证它与当前入口 session 是同一个用户，再在本次请求中转发给 MaaS 网关。不能只读未验签的 JWT 字段。浏览器直接跨域请求网关需另核实 CORS | 页面仅带入口 cookie；入口按当前 session 取密文、解密，再向固定 MaaS 分享网关发 Bearer 请求 |
| 页面脚本可读性 | 同源 JavaScript 能读 token；XSS 或被攻破的同源脚本可能窃取完整 MaaS 登录凭据 | 页面脚本读不到 MaaS token；XSS 仍可能借当前登录态发起操作，入口仍需权限校验 |
| 入口重启/多副本 | 在线用户每次请求重新带 token，可跨入口副本；后台清理若靠内存缓存则重启/换副本会丢 | 有效 session 的 token 可从共享 PG 读取；多副本可共用会话数据 |
| 退出与过期 | 页面退出清理 `localStorage`，入口 session 失效；已泄露的 token 不会因此自动从上游失效；到期需重新登录 | 退出删除本 session 及其加密 token；到期拒绝使用并重新登录；上游是否撤销仍取决于 MaaS 接口 |
| 改动重点 | 登录响应与前端认证存储、双身份一致性、所有分享请求携带 token、退出清理 | PG migration、登录事务、加密存储、按会话读取、过期/退出清理；前端分享 API 不接触 MaaS token |
| 对已有 Hermes 设计的影响 | 改变当前“浏览器只持有入口 session”的边界，前端必须保护另一项高权限凭据 | 延续当前边界和 `CredentialCipher` 使用方式，但入口与数据库承担凭据保管责任 |

**建议选择方案二。** 它能复用当前入口会话和已有加密机制，避免把 MaaS 登录凭据暴露给浏览器脚本。首期按 session 保存，不默认允许用户退出后继续使用。数据库密码或数据库自身鉴权是另一件事，不妨碍加密数据入库。

**两方案共同未解决的点：** 当前分享网关上传接口没有提供服务端 TTL；若分享链接到期时用户 MaaS token 已过期或退出，后台 DELETE 可能失败。要可靠承诺“到期后不可访问”，需分享网关原生到期控制，或受限的后台删除授权。也要确认上游 token 是否可刷新以及重新登录对其他设备的影响。

## 1. 先看结论

**“迁移分享功能”不等于“必须保存 MaaS token”。** 当前桌面确实携带 MaaS 登录 token 调用分享网关，但这是已存在的接入方式，不足以证明独立分享服务只能接受这一种认证。

建议按目标选择：

- **优先复用桌面现有业务接口，同时推进首页、套餐等能力：** 推荐入口加密持久化 token，首期绑定当前入口登录会话使用。
- **只想先迁移分享，而且分享服务已支持服务间认证：** 可以不保存用户 MaaS token，由入口校验用户与分享归属后调用分享服务。
- **需要退出登录后仍自动执行账号业务：** 这是额外的后台授权决定，不能仅因为保存了 token 就默认允许。还需要解决 token 到期、撤销和后台任务持续授权。

当前应先确认分享网关/服务端支持的认证方式，再确定分享是否依赖 token 保存。该确认不影响开展前端桥接、会话快照和实例产物来源校验的设计。

## 2. token 是什么，当前到底保存了什么

这里的 MaaS token 指短信登录接口 `/app/login/smsLogin` 返回的 `token`，不是套餐的模型调用密钥。

| 凭据 | 当前用途 | 云端当前状态 |
|---|---|---|
| MaaS 登录 token | 桌面以用户身份调用分享、首页配置等业务接口 | 登录请求中短暂使用，没有传入入口持久化流程 |
| 套餐 API key | 调用模型，使用用户套餐额度 | 加密保存到 `tenant_credentials.api_key_ciphertext` |
| 入口 session | 浏览器访问云端时确认登录用户 | 入口自行生成随机值，数据库保存哈希，浏览器持有 cookie |
| 实例 token | 入口认证访问用户实例 | 已有独立加密存储 |

它们各自有不同验证方、权限和生命周期。保存了套餐 API key，不代表保存了 MaaS 登录身份；入口 session 也不能直接拿去请求 MaaS。

### 已由当前代码确认的事实

1. 云端 `app.py::login` 获取 `result.token`，调用 `my_plan(result.token)` 获取套餐，再将 `api_key`、用户 ID、有效期等传入 `_finish_login`，不传 token。
2. `store.py::finish_login` 加密保存套餐 key，并保存入口 session 哈希和上游到期时间，没有保存 MaaS token。
3. 入口会话到期时间目前取配置的 session TTL 与上游到期前五分钟的较早值。保存上游到期时间不代表保存了令牌本身。
4. 云端退出目前删除当前入口 session 并清 cookie，不是撤销 MaaS 上游登录，也不会因此删除所有用户凭据。
5. 桌面登录保存身份，其中包含 token；会话和产物分享均注入 `currentDesktopIdentity().token`。
6. 桌面分享客户端向 `https://maas.ai-yuanjing.com/app/gateway/uniclaw-shares/{shareId}.html` 发 PUT/DELETE，并携带 `Authorization: Bearer <token>`。
7. 桌面首页配置也使用登录 token，请求 `welcome_config_v3_zh-CN` 或 `welcome_config_v3_en`。
8. 云端已有基于 Fernet 的 `CredentialCipher`，可以复用；不必从零实现加密存储。

### 尚未确认的事实

- 分享鉴权发生在 MaaS 网关还是分享服务内部，token 是否继续透传。
- 分享服务是否支持入口直接调用、服务凭据、用户身份委托或短期交换凭据。
- 上游是否提供 refresh token、刷新接口、撤销接口或权限范围更窄的业务 token。当前核查路径未发现刷新实现，不等于服务端一定没有。
- 一个用户重新登录是否使其他设备拿到的 token 失效。
- 分享服务是否持久化发布者身份，并校验更新、删除权限。
- 分享服务是否支持原生到期失效。

以上不能由域名或客户端传参反推出结论；需要服务端代码、接口契约或测试环境联调证实。本次没有读取生产凭据或验证线上服务。

## 3. 保存 token 带来的收益和责任

收益是入口可以在登录之后继续以用户身份调用现有业务接口。浏览器不必持有 MaaS token，用户也不必每次分享都重新短信登录。

但入口将持有一项可代表用户执行操作的凭据。需要明确：

- 哪些功能允许使用它，谁决定当前用户；
- 保存多久，退出、过期和账号禁用时如何处理；
- 多设备登录互相影响与否；
- 后台任务是否有权在用户离线后继续使用；
- 加密密钥的保管、备份、轮换，以及日志脱敏。

加密可以降低数据库单独泄露时的风险，但拥有密文和解密主密钥的入口仍然能读取 token。不能把“加密保存”解释为入口无法接触明文。

## 4. 四种方案对比

| 方案 | 实现方式 | 优点 | 局限 | 适合场景 |
|---|---|---|---|---|
| A：保持不保存 | 登录时只查套餐，之后不持有 MaaS token | 维持现状，入口不新增用户登录凭据 | 需要 token 的后续业务不能直接复用；每次重新认证体验差 | 暂不开放这些业务 |
| B：仅内存保存 | token 按会话保存在入口进程内 | 不落数据库，单进程原型较简单 | 重启丢失；多副本请求可能落到无 token 的进程；仍需过期和退出处理 | 短期验证，不建议作为正式默认方案 |
| C：加密持久化 | token 和有效期存 PG，入口按登录会话读取 | 可复用桌面接口，支持入口重启和多副本 | 需实现凭据生命周期与会话隔离；不自动解决续期 | 多项 MaaS 业务迁移，推荐的兼容路线 |
| D：服务间认证/受限委托 | 入口使用受支持的服务身份或交换凭据调用业务服务 | 分享可不依赖用户 MaaS 登录 token；后台能力可单独授权 | 必须有服务端支持；入口/服务端要落实用户归属与权限，不能只加一个 user_id 参数 | 自有分享服务可配合改造或已有正式接入契约 |

D 不意味着无需凭据管理，而是改为管理服务凭据。其影响范围可能大于单用户 token，需要按业务限制调用权限。也不能未经确认就绕开原网关的限额、审计或用户权限检查。

这些方案可以按业务组合：分享采用 D，套餐采用 C；没有必要强迫所有服务采用同一种认证。

### UniClaw `cloud-vm-dev` 的做法与浏览器风险

核查本地 `cloud-vm-dev @ eed444b2`：其前端 `useAuth.ts` 将登录 token 写入 `localStorage["auth_token"]`，业务请求以 Bearer token 交给后端；后端 `AuthMiddleware` 把 token 放入当前请求的 `ContextVar`，分享存储再转发到 MaaS 网关。为到期清理，后端还按用户在进程内缓存最多 256 份未过期 token。这是该分支的实现事实，不代表 Hermes 应照搬。

浏览器 `localStorage` 可由同源运行的 JavaScript 读取。若页面发生 XSS，或同源第三方脚本被攻破，攻击代码可以读取并转走 MaaS token；清除页面或退出账号之前，令牌也会跨标签页和浏览器重启保留。通过 HTTPS 传输、短有效期和 CSP 能降低部分风险，不能把 `localStorage` 变成对同源脚本不可读的存储。后端内存缓存也无法在进程重启后继续可靠执行分享清理。

Hermes 云端现有入口 session cookie 已能代表当前浏览器登录。若决定保存 MaaS token，优先由入口接收后加密保存，业务调用由入口代发；浏览器继续只持有入口 session。Cookie 需保持 `HttpOnly`、`Secure`、合适的 `SameSite` 与作用域，并对写请求校验来源/CSRF。这样可以避免把 MaaS token 暴露给页面脚本；XSS 仍可能在用户登录期间发起其有权限的操作，所以服务端归属检查、固定业务接口和页面防注入仍然必要。

如果分享服务提供受限的服务间认证，分享可走方案 D，连入口也无需为分享保存用户 MaaS token。若必须使用当前网关的用户 Bearer token，则按第 5 节的会话绑定方式实现。

## 5. 如果采用 C，推荐怎样保存

### 推荐首期：按入口登录会话绑定

可以在现有 `auth_sessions` 增加可空的加密 token 字段，或使用与 session 关联的凭据表；复用 `CredentialCipher`。具体表结构在实施时根据迁移兼容性确定。

建议保存：加密 token、上游到期时间，以及用于识别更新/失效的必要元数据。已有用户归属、会话创建时间能复用就不重复存。不要把 token 写入用户实例 `.env`、浏览器存储、通用 API 响应或审计日志。

为何首期按会话而非用户共享一份：

- 当前设备退出，直接删除对应 session 和凭据，不影响其他设备的入口 session。
- 不会出现一个设备重新登录，就静默替换另一个设备正在使用的身份凭据。
- 当前登录用户发起请求时，授权关系明确。

这只能保证入口侧语义；如果 MaaS 上游本身只允许单 token，其他设备仍可能被上游置为失效，需要按真实契约处理。

### 用户级保存何时才合适

当产品明确要求用户离线或退出后，入口仍以账号身份运行后台业务，并有明确授权与续期机制时，再考虑用户级凭据。

用户级保存必须先定义：使用最新哪次登录的凭据、单设备退出是否保留、全部退出如何处理、并发刷新与失败如何避免删除新凭据。不是简单地在 `tenant_credentials` 增加一列就完成。

## 6. 推荐生命周期规则

以下是采用 C、会话绑定时的建议行为，不是当前已经实现的功能。

| 事件 | 建议处理 |
|---|---|
| 短信登录成功 | 校验上游有效期，事务内创建 session 并保存加密 token |
| 存储失败 | 不返回“新会话登录成功”；保留原有效会话，不写入半成品 |
| 旧会话没有 token | 明确提示需要重新登录以使用相关功能，不能拿模型 key 顶替 |
| 用户发起业务请求 | 从当前 session 解析用户，确认有效期，读取对应 token；校验目标会话/文件/分享归属 |
| 关闭网页 | 不等于退出登录；session 按既定有效期存在，已发布链接由分享服务提供 |
| 当前设备退出 | 失效当前 session，删除对应 token；阻止新的代调请求 |
| 请求进行中退出 | 尽可能取消未完成请求；外部写入可能已经发生，要记录待确认结果，不能声称一定未发布 |
| token 到期 | 拒绝继续使用，提示重新登录；不擅自延长，也不假设存在自动刷新 |
| 上游明确返回认证失效 | 仅失效本次使用的凭据版本，避免迟到错误覆盖新登录结果 |
| 网络超时或普通服务错误 | 返回可重试故障，不直接删除 token，不统一当作退出登录 |
| 账号禁用/全部退出 | 失效该用户全部入口 session 和对应 token；是否撤销上游登录取决于其接口支持 |
| 入口重启/扩容 | 通过共享数据库恢复有效 session 对应的凭据，无需依赖单进程内存 |
| 备份恢复 | 不自动恢复已过期凭据；需考虑已撤销 session 在旧备份中的复活，恢复流程应明确是否强制重新登录 |

特别注意：`maas.py` 的现有契约说明记载，上游曾对无效 token 返回 500。不能直接写成“所有 500 都清除登录”；认证失效应依据已确认的业务错误码/响应契约判定。

后台任务不要隐式借用“任意一个还活着的浏览器 session”。若需要后台身份，应单独设计授权和凭据来源。

## 7. 对分享迁移的具体影响

### 会话分享

如果继续使用桌面现有网关，入口需要取得该网关认可的身份。采用 C 可以复用当前用户 token；采用 D 则需要服务端明确认可服务身份及用户委托。

不管采用哪种认证，都仍需：实例生成可信快照、入口验证会话归属、发布前检查版本、保存待确认记录、幂等重试和可靠撤销。这些不是保存 token 后自动具备的能力。

### 产物分享

除认证之外，还需要迁移实例侧来源记录与摘要校验，保留“上传文件、派生产物和未知来源不得直接发布”的现有规则。token 只回答“谁在请求”，不能回答“这个文件是否允许分享”。

### 到期删除是单独的决策点

当前桌面上传请求没有把 TTL 传给分享网关；产物有效期记在本地，到期后通过用户 token 调 DELETE。

因此：

- 用户退出后删除 session token，后台清理将没有这份凭据。
- 即使把 token 保留到后台使用，它也可能先于分享期限过期。
- 所以“加密保存 token”不能保证分享按时不可访问。

优先让分享服务原生执行有效期，或提供权限受限的服务端删除能力。若均不支持，只能明确提供有失败可能的到期清理与重试，不能把页面上的“已过期”当成公网访问已经失效。正式承诺有效期之前必须解决这一点。

已上传的分享页面是否继续可访问，由分享服务的访问策略决定。不要把 token 到期、浏览器退出与撤销分享混为一谈。

## 8. 入口代码应承担什么

沿现有结构扩展即可：

| 位置 | 修改职责 |
|---|---|
| `entry/entry/app.py` 登录路径 | 将登录 token 纳入事务保存；页面只得到入口 session |
| `entry/entry/store.py` 与 migrations | 保存、读取、过期和删除会话绑定凭据，兼容旧 session |
| `entry/entry/crypto.py` | 复用认证加密；评估主密钥轮换和备份方式 |
| `entry/entry/maas.py` 或具体业务模块 | 用当前会话身份调用固定业务接口，处理超时及准确的认证错误 |
| 浏览器 bridge | 调入口业务 API，拿业务结果，不拿 token |
| 分享业务存储 | 保存归属、分享 ID、版本、状态与失败恢复信息，不能依赖进程内 Map |

入口不提供一个“传 URL 就带 token 代请求”的通用接口。每项业务限定目标、请求字段和操作权限；浏览器提供的 user_id、profile、路径或 shareId 都不能绕过归属检查。Cookie 认证的写接口沿用并核验入口的来源/CSRF 防护。

## 9. 决策前向服务端确认的问题

| 问题 | 答案影响 |
|---|---|
| `/gateway/uniclaw-shares` 在哪一层验证 token？ | 确定独立分享服务是否依赖 MaaS 身份 |
| 是否支持云端入口的服务间认证或短期委托？ | 决定分享能否走 D，不保存用户 token |
| 服务端如何绑定分享的发布者，谁能覆盖/删除？ | 防止入口接入后失去用户隔离 |
| 是否支持服务端 TTL，是否有到期后实际拒绝访问的保证？ | 决定能否可靠提供有效期 |
| 登录 token 有效期、刷新、撤销和多设备语义是什么？ | 决定 C 的生命周期与后台能力范围 |
| 能否使用权限更窄的分享凭据？ | 避免保存全账号权限 token，仅为单项功能授权 |

## 10. 建议的决议与实施顺序

**建议决议：若要优先兼容当前桌面接口，采用 C 的会话绑定加密持久化；不默认授予退出后的后台权限。分享服务如果已有 D 的正式接口，则分享优先使用该接口，不以保存 MaaS token 作为前置阻塞。**

实施顺序：

1. 确认上表中的服务端契约，尤其分享认证与到期失效。
2. 确定会话绑定还是用户级保存，以及退出后的业务范围。
3. 若选择 C，补数据库迁移、登录保存、读取/过期/退出处理；旧 session 不强制全量登出，使用新业务时引导重新登录。
4. 用一个真实只读账号业务接口验证身份链路，再接分享发布与撤销。
5. 验证双用户隔离、多设备退出、重启、多副本、认证失效与上传结果不确定的恢复。

验收不只看 mock：用测试账号、临时数据库和两个独立用户环境跑 A→B→A；检查 token 不出现在浏览器响应和日志中。Python 测试使用仓库 `scripts/run_tests.sh`。本次文档整理不执行生产登录或发布操作。
